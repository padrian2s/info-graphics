The one thing everyone agrees on

consensus

LLMs don't usually fail at syntax. They fail at invisible assumptions about architecture, constraints, and invariants. A written plan becomes a debugging surface for those assumptions.

The core tension

debate
Plan-first camp — "Never let Claude write code until you've reviewed and approved a written plan."
Iterate camp — "Small issues with clear details? Claude can go to town. You don't review every decision a teammate makes."
Skeptic camp — "All this planning and prompting is far more work than just writing the code yourself."

What actually works (consensus techniques)

practitioner-tested
1

Surface assumptions before they become code

LLMs fail at invisible constraints and invariants. A written plan is a debugging surface for architectural assumptions. Get them wrong on paper, not in a 2,000-line diff.

2

Work in batches of ≤1,500 lines

One developer's 30,000 LOC app has ~100,000 lines of plan behind it. Can't build something that big as a one-shot. Break plans into complexity-bounded batches.

3

Annotations in-context are powerful

"This should be two slides." "Use a side-by-side layout here." "Pull the code example from ../examples/foo." Token distance in-context makes inline annotations extremely effective.

4

Build a living knowledge base

Every time you correct the model, update persistent guidance so it doesn't repeat the mistake. Turn one-off corrections into durable rules. CLAUDE.md, memory files, skills.

5

Clear context between phases

Restart sessions between planning levels. Fresh context often finds new issues and things to clarify before the next phase. Stale context accumulates drift.

Layered documentation (large projects)

multi-pass

▶ Architecture & requirements → iterate until satisfied

▶ Design document → clear context, iterate

▶ Implementation plan (≤1,500 lines per batch) → clear context, iterate

▶ Code execution + tests → atomic commits, verify

The honest criticisms

what pushed back

"Nothing radically different here"

Multiple commenters pointed out the viral article's workflow is exactly what Anthropic recommends as best practice. The framing as revolutionary was seen as AI-written hype. Same ideas have been written about dozens of times.

"More work than just writing the code"

For experienced developers, the overhead of planning, prompting, checking, and orchestrating can exceed the cost of just writing the code yourself. "There's no winner for 'least code written regardless of productivity outcomes.'"

"Prompt magic is superstition"

Debate over whether words like "deeply" and "intricacies" actually change model behavior or are confirmation bias. Evidence suggests framing does influence attention patterns, but results are probabilistic, not deterministic.

"Big bang is fragile"

Writing the entire plan then executing monolithically produces thousands of lines nobody understands. If the plan is wrong, you start over from scratch. Multiple devs strongly preferred incremental execution.

"Where are the tests?"

The original article mentioned only "quick checks" — no comprehensive tests. Community consensus: tests are non-negotiable. TDD with AI (write tests first, implement second) gets strong advocacy.

What the thread rediscovered

old lessons, new context

Several experienced developers noted this workflow rediscovers fundamental software engineering principles — smaller iterations, atomic commits, thorough planning, TDD — that had fallen out of practice during rapid prototyping eras. AI didn't invent good engineering. It made good engineering mandatory again because the cost of sloppy specification is now a 2,000-line wrong diff instead of a 20-line wrong function.

The tools people mentioned

emerging ecosystem
Spec-first tools

Amazon Kiro, Google Antigravity, GitHub Spec Kit, OpenSpec — all automate the plan-then-execute pattern. Antigravity even includes UI for annotating plans. But models sometimes silently downgrade specialized requirements.

Multi-model workflows

Using GPT for planning/exploration to bootstrap conversations with Claude for execution. Helps form better questions and derisk usage limits. "I'm having richer conversations now because I'm more confident in my prompts."
